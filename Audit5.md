Là où je serais franchement critique : le scope est trop large pour une V1 lisible. Le repo raconte en même temps un ADK généraliste, un moteur de topologies, un système mémoire 4 tiers, un lab de benchmark, un pipeline arXiv/RAG, un serveur A2A/MCP et une UI. C’est impressionnant, mais un visiteur ne sait pas immédiatement si YGN-SAGE est un framework de recherche, un runtime infra ou un produit applicatif.

Ton autre point faible, plus dangereux, c’est la cohérence documentaire. Dans le même README, on lit “Templates (x8)” puis 11 patterns listés plus bas; dans sage-core/src, la doc parle encore de 8 templates; la flow globale affiche 6 étapes jusqu’à LEARN alors que pipeline.py est décrit comme une pipeline primaire en 5 étapes; sage-python annonce Python 3.12+, mais pyproject.toml demande >=3.11; la doc CI parle de 691 tests Python alors que le README de sage-python affiche 1426 passés, 111 skipped et 7 échecs préexistants. Même le récit du routing est un peu brouillé, le README mettant en avant un kNN “primary” à 92% GT tandis que sage-core/src présente aussi SystemRouter comme “PRIMARY” à 88% GT. Pour un projet qui met en avant vérification et rigueur, ça entame la confiance.

Erreurs et problèmes concrets que j’ai repérés dans le code :

compute_importance_score() n’exclut pas la sortie du nœud courant par index, mais par valeur (o != result). Si deux workers rendent exactement le même texte, other_outputs peut devenir vide et le nœud sera noté à importance 1.0, ce qui fausse le pruning.
Dans l’upgrade de modèle, si le chargement de config/cards.toml échoue, TopologyController met new_model_id = fallback, où fallback vaut "reasoner", "fast" ou "budget". Or la config providers manipule des IDs concrets comme gpt-5.4, gemini-3.1-flash-lite-preview ou grok-4-1-fast-reasoning. Tu peux donc produire un “upgrade” non exécutable.
Dans SystemRouter::route_integrated(), le commentaire dit en substance “utiliser le modèle du bandit s’il est dans les candidats, sinon fallback”, mais le code renvoie quand même bd.model_id.clone(). Donc le bandit peut contourner le filtrage candidat/contraintes.
RoutingConstraints expose un security_label, mais apply_constraints() ne filtre que coût, latence, qualité et capacités (tools, json_mode, vision). Aujourd’hui, ce champ a l’air non appliqué.
Tu as une divergence de contrat entre couches : le routeur Rust filtre la capability json_mode, tandis que ModelAssigner cherche json. Les deux couches peuvent donc aboutir à des décisions incohérentes sur le même besoin de sortie structurée.
Ton smoke test d’intégration réelle est mal branché : le job CI integration-smoke ne s’exécute que sur refs/heads/master, alors que le repo est sur main, et il est en plus continue-on-error: true. En pratique, tes régressions API réelles peuvent passer sans bloquer.
