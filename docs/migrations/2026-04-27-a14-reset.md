# A14 Bandit Posterior Reset — Migration Runbook

**Date**: 2026-04-27
**Trigger commit**: `48dc7c3f` (`fix(bandit): make Python pipeline learning causal`)
**Reset script**: `scripts/a14_reset_bandit_state.py`
**Source-of-truth review**: cgpro 2026-04-26 (`cgpro_2026_04_26_review` conversation)

## Why reset?

A14 closed two compounded bugs in the bandit recording chain:

1. **Off-policy attribution.** Stage 0 of the Python pipeline routed via
   `SystemRouter::route()` — the legacy API that doesn't consult the
   bandit. Stage 4 then called `bandit.select_with_context()` separately,
   captured only `decision_id`, and dropped the chosen `(model_id,
   template)` pair. Stage 5 recorded outcomes against the orphan id —
   posteriors updated for arms whose model never executed.
2. **PyO3 method-name mismatch.** `bandit.rs` exposes the recording
   method as `#[pyo3(name = "record")]` but `pipeline.py:1759` checked
   `hasattr(self.bandit, "record_outcome")`. The check always returned
   False, so the legacy block was a no-op since it was written. The
   bandit recorded **nothing** from production traffic.

A14 introduces `record_outcome_checked` that refuses off-policy
attribution at the API boundary, plus a single-agent-only causal
selection path. From `48dc7c3f` forward, posteriors update only when
the executed `(model_id, template)` matches the selected one.

But the historical SQLite state cannot be salvaged. The legacy schema
only stored `decision_id` per outcome — it did not store the selected
`(model_id, template)` *and* the executed `(model_id, template)`
side-by-side. Without both halves, no audit can prove the ≥95% causal
attribution threshold cgpro set as the bar for keeping state. cgpro's
verdict: **unverifiable state must be reset by default**.

## What the reset does

`scripts/a14_reset_bandit_state.py` operates on a single SQLite file
(typically `~/.sage/bandit_state.sqlite`, but the actual path is
deployment-specific — pass `--db <path>`).

Two reset modes:

### Default — targeted truncate (recommended)

`--apply` (without `--full-reset`):

1. Take a timestamped full-file backup:
   `bandit_state.sqlite` → `bandit_state_pre_a14_reset_YYYYMMDD_HHMMSS.sqlite.bak`
2. `DELETE FROM bandit_arms` (drops all per-arm Beta/Gamma posteriors
   plus per-arm context running statistics).
3. `VACUUM` to release disk space.
4. **Preserves** `bandit_config` so any explicit `decay_factor` or
   `exploration_bonus` overrides survive.

After this, the next bandit boot will warm-start from `cards.toml`
affinities (see `sage-python/src/sage/boot_topology.py`) and start
collecting causal posteriors fresh.

### Alternative — full reset

`--apply --full-reset`:

1. Take the same timestamped backup.
2. `mv bandit_state.sqlite bandit_state_pre_a14_full_reset_YYYYMMDD_HHMMSS.sqlite`
   (the original file is moved aside, not just truncated).
3. Next boot creates a brand-new DB from scratch.

Use this if you want to drop `bandit_config` overrides too, or if the
schema has drifted in unexpected ways from `bandit.rs::persistence`.

## Procedure

### 1. Inspect state (read-only)

```bash
python scripts/a14_reset_bandit_state.py \
    --db /path/to/bandit_state.sqlite \
    --dry-run
```

Reports DB size, schema tables, and row counts. Make a copy of the
output for the post-mortem.

### 2. Schedule a maintenance window

The reset itself is fast (single `DELETE` + `VACUUM` on a small table)
but the next-boot warm-start triggers a brief learning cold-start. If
your deployment routes traffic via the bandit, expect ~exploration_budget
fraction of decisions to be exploratory rather than exploitative for
the first ~10–100 outcomes per arm.

### 3. Stop the YGN-SAGE process(es)

The reset script opens the SQLite file directly. If a live process has
the WAL journal open you may end up with stale state. Stop processes
before applying.

### 4. Apply

```bash
python scripts/a14_reset_bandit_state.py \
    --db /path/to/bandit_state.sqlite \
    --apply
```

Or for a full reset:

```bash
python scripts/a14_reset_bandit_state.py \
    --db /path/to/bandit_state.sqlite \
    --apply --full-reset
```

### 5. Verify

The script's tail prints the post-reset state — `bandit_arms` row count
should be 0 (truncate mode) or the table should not appear (full-reset
mode, since the file was moved aside).

### 6. Restart YGN-SAGE

The bandit will rebuild posteriors from `cards.toml` warm-start
affinities on first boot, then collect causal outcomes from the A14
pipeline going forward.

## Rollback

If anything goes wrong, the backup is the original file:

```bash
# truncate mode
cp /path/to/bandit_state_pre_a14_reset_YYYYMMDD_HHMMSS.sqlite.bak \
   /path/to/bandit_state.sqlite

# full reset mode
mv /path/to/bandit_state_pre_a14_full_reset_YYYYMMDD_HHMMSS.sqlite \
   /path/to/bandit_state.sqlite
```

## Why this is operator-driven, not auto-applied in CI

Resetting accumulated learning state is a deployment decision, not a
build-system decision. Different operators may want different rollout
strategies:

- single-instance dev: reset immediately, tolerate cold-start.
- staging: reset on next deploy, observe convergence over a week.
- prod with traffic: reset during low-traffic window, monitor metrics.

This script is committed to the repo as a tool. The reset itself is
the operator's decision — see `MEMORY.md` "Open follow-ups" → "A14-reset"
for status.
