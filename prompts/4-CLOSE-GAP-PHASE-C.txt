Tu travailles sur le repo YGN-SAGE, branche VeRLGIGPO.

Mission
Je ne veux pas une régression de fonctionnalités.
Je veux réduire le gap entre les ambitions du projet et l'implémentation réelle.
Tu dois donc préserver les capacités utiles déjà présentes, mais les rendre plus concrètes, plus cohérentes, plus branchées, plus testables, et plus honnêtes.

Objectif produit à atteindre
YGN-SAGE doit se rapprocher concrètement de ce résultat :
- génération de topologie agentique réellement adaptative,
- multi-agent,
- multi-provider / multi-model,
- training Nemotron qui améliore réellement ces décisions,
- runtime qui consomme honnêtement ce que le training produit.

Important
Ne repars pas d'un audit "table rase".
Les précédentes corrections existent peut-être déjà.
Tu dois d'abord vérifier l'état courant pour éviter de casser des fixes déjà faites.
Ensuite seulement tu patches le minimum utile pour rapprocher le projet du résultat voulu.

Règles de non-régression
- Ne supprime pas une capacité existante juste pour rendre le repo "plus propre".
- Ne remplace pas un composant riche par une version simplifiée si ce n'est pas strictement nécessaire.
- Ne casse pas les chemins multi-agent, multi-provider, Path 6, pipeline 5 stages, model assignment, provider pool, bandit, mémoire, ou training scripts sans remplacement équivalent et tests.
- Ne commence pas par README ou AI-ARCHITECTURE.
- Pas de doc-only fix.
- Pas de faux fix par fallback silencieux.
- Pas de mock/stub compté comme capacité livrée.
- Pas de refactor large si un patch ciblé suffit.
- Si une capacité ne peut pas être finalisée honnêtement tout de suite, rends sa surface explicite au lieu de prétendre qu'elle est finie.

Hypothèse stratégique par défaut
Le plus court chemin non régressif est probablement :
- conserver Phase A / V5 comme warm-up one-shot ou prior,
- rendre Phase C vraiment exploitable comme phase dynamique multi-step,
- faire de la version custom Phase C le chemin runnable immédiat si c'est le chemin le plus réaliste,
- garder l'intégration verl-agent comme accélérateur optionnel futur, pas comme prérequis bloquant pour prétendre que Phase C existe.

Tu peux contester cette hypothèse seulement si le code actuel prouve qu'une meilleure option est plus simple, plus sûre, et plus proche de l'objectif.

Ce que tu dois fermer en priorité
1. Contradiction Phase C
Le repo ne doit plus avoir une "Phase C fallback/custom" qui prétend marcher sans verl-agent si elle est bloquée par l'environnement réel.
Tu dois soit :
- rendre cette Phase C custom réellement runnable sans verl-agent dans un mode honnête et non réservé aux tests,
- soit séparer proprement les modes et arrêter toute ambiguïté.

2. Contrat training -> policy artefact -> runtime
Le schéma de sortie de policy doit être cohérent avec :
- le training,
- le parsing,
- la construction du graphe,
- l'assignation de modèles/providers,
- l'exécution runtime,
- le reroute/adaptation.
Je veux un contrat unique, validé, réutilisé.

3. Dynamique topologique concrète
Je veux réduire le gap vers une adaptation réellement dynamique.
Mais je ne veux pas une réécriture totale fragile.
Donc :
- si une mutation in-place limitée est faisable sans gros risque, implémente-la pour les cas utiles,
- sinon garde la sémantique actuelle mais rends-la explicite et exploitable,
- ne présente jamais une régénération externe comme une mutation in-place.

4. Multi-provider / multi-model
Cette dimension ne doit plus être seulement un détail annexe.
Sans tout réécrire, elle doit entrer à un endroit défendable :
- soit dans le contrat de topologie,
- soit dans l'espace d'action,
- soit dans les métadonnées d'adaptation,
- soit dans le chemin runtime mesuré et testé.
Au minimum, la policy/topologie doit pouvoir exprimer quelque chose d'utile au sujet du choix de modèle/provider, et le runtime doit le consommer réellement.

5. Reward / modes d'exécution
Je veux une séparation propre entre :
- reward structurelle,
- reward exécution simulée,
- reward exécution réelle.
Si le mode annoncé est "réel", un fallback structurel silencieux n'est pas acceptable.
Il doit devenir :
- soit une erreur explicite,
- soit une pénalité explicite et traçable,
- avec une raison de fallback loggée et testée.

6. Learning loop utile
Je ne veux plus de boucle d'apprentissage "à moitié vraie".
Tu dois traiter explicitement :
- enregistrements avec quality neutre par défaut,
- enregistrements sans embedding utile,
- backend mémoire mock,
- bandit/télémétrie purement en mémoire si elle est utilisée pour justifier de l'apprentissage continu.
Objectif : ne pas mentir, et améliorer la réutilisation réelle des signaux.

7. Tests et CI
Je veux une preuve plus forte.
Renforce les tests faibles.
Ajoute un smoke path réaliste pour la Phase C / contrat policy-runtime / scénario dégradé.
La CI doit mieux protéger la branche de travail ou les chemins critiques concernés.
Évite les jobs critiques "continue-on-error" si ce sont eux qui sont censés prouver la capacité.

Workflow obligatoire

Phase 0 — Vérification ciblée, lecture seule
Sans modifier de fichiers :
1. Affiche :
   - branche courante,
   - commit SHA exact,
   - git status,
   - fichiers modifiés non commités s'il y en a.
2. Identifie les vrais entrypoints :
   - serving runtime,
   - training offline,
   - tests / benchmarks / CI.
3. Vérifie rapidement, sans re-auditer tout le repo, les points suivants :
   A. La Phase C custom est-elle réellement runnable ?
   B. Le contrat Path 6 / Nemotron / V2 / artefact runtime est-il cohérent ?
   C. Le runtime exécute-t-il vraiment le pipeline principal avant fallback ?
   D. Le reroute est-il encore une reconstruction externe ?
   E. La quality pipeline est-elle encore dépendante de defaults/abstention/heuristique ?
   F. La mémoire et la boucle de learning ont-elles encore des trous matériels ?
   G. Le multi-provider est-il visible dans le contrat réellement servi ?
   H. Les tests/CI prouvent-ils les claims restants ?
4. Pour chaque point A-H, donne :
   - verdict court,
   - fichier(s) et symbole(s),
   - impact si laissé en l'état,
   - correction minimale honnête.
5. Ensuite seulement, propose un plan de patch.

Format attendu pour chaque constat matériel :
[EVIDENCE: path:lines ; symboles]
[STATUT: Observé | Inféré | Inconcluant]
[REACHABILITY: Runtime | Training | Dead code | Inconnue]
[VALIDATION: Test | Benchmark | Pipeline | Aucune]

Phase 1 — Choix stratégique
Choisis UNE stratégie principale et justifie-la.
Par défaut, préfère :
Option A
- Phase A/B = warm-up one-shot,
- Phase C custom = vrai chemin dynamique runnable maintenant,
- verl-agent = chemin futur optionnel / accélérateur.

Tu peux choisir une autre option seulement si elle est objectivement meilleure sur :
- effort,
- risque de régression,
- proximité avec l'objectif multi-agent + multi-provider + topologie dynamique,
- compatibilité avec le runtime actuel.

Ta stratégie doit expliciter :
1. observation space,
2. action space,
3. granularité du crédit,
4. reward decomposition,
5. schéma d'artefact policy,
6. schéma de graphe runtime,
7. place du multi-provider,
8. stratégie de fallback honnête,
9. stratégie de validation.

Phase 2 — Plan de patch
Avant tout edit, produis un plan séquencé.
Ordre de priorité impératif :
1. refermer le contrat Phase C / env / script / runtime,
2. unifier le schéma policy -> graph -> runtime -> reward,
3. rendre explicites les modes structural / simulated / real,
4. intégrer le multi-provider au bon niveau sans réécriture massive,
5. renforcer tests et CI,
6. mettre la doc à jour en dernier.

Pour chaque patch :
- fichiers touchés,
- comportement cible,
- test ajouté ou renforcé,
- risque,
- critère d'acceptation.

Phase 3 — Implémentation
Ensuite seulement, implémente.

Exigences détaillées

A. Phase C concrète
Tu dois fermer la contradiction actuelle.
Si la Phase C custom reste le chemin choisi :
- elle doit pouvoir s'exécuter honnêtement hors SAGE_TESTING,
- ou disposer d'un mode explicite et officiel qui remplace proprement ce contournement,
- avec un vrai smoke test.
Si verl-agent reste nécessaire pour une sous-variante :
- cela doit être explicite,
- ce ne doit pas invalider l'existence d'une Phase C runnable sur cette branche.

B. Contrat unique de topologie
Crée ou renforce un schéma partagé pour au moins :
- nodes,
- edges,
- difficulty,
- reasoning,
- adaptation/checkpoints,
- model_tier,
- et, si faisable sans explosion de complexité, provider_preference / provider_constraints / allowed_providers.
Ce schéma doit être consommé par :
- la policy,
- le training env si pertinent,
- le runtime stage topology,
- le runner / assigner,
- les tests.

C. Multi-provider concret
Je ne veux pas une réécriture d'algorithme complète.
Je veux une intégration défendable.
Donc privilégie un design pragmatique :
- la topologie/policy peut exprimer une préférence ou contrainte provider/model,
- Stage 3 l'interprète réellement,
- les scénarios provider indisponible / circuit open sont testés,
- la décision ou le fallback sont traçables.

D. Adaptation honnête
Ne mens pas sur la granularité.
- Si tu peux implémenter une mutation in-place limitée et sûre pour certains checkpoints utiles, fais-le.
- Sinon, conserve la régénération mais rends-la explicite dans les noms, traces et tests.
- Dans tous les cas, ne dégrade pas les capacités existantes.

E. Reward honnête
Sépare clairement les modes :
- structural,
- simulated_exec,
- real_exec.
En mode real_exec :
- pas de succès silencieux en fallback structurel,
- erreur ou pénalité explicite,
- info de traçabilité présente dans logs/metrics/tests.
Si un mélange pondéré est conservé, il doit être explicitement nommé et non vendu comme "pure execution reward".

F. Learning loop plus concrète
Réduis le faux apprentissage.
Tu dois traiter prioritairement :
- quality neutre injectée par défaut,
- embeddings manquants,
- mémoire mock,
- télémétrie non persistée si elle est utilisée pour justifier du learning.
Je ne demande pas forcément une persistance totale partout.
Je demande que les claims et les chemins actifs soient cohérents.

G. Tests
Renforce ou remplace les tests faibles.
Je veux au minimum :
1. nominal :
   - policy/graph/runtime alignés,
   - Phase C choisie lance au moins un épisode multi-step,
   - modèle/provider assignment consommé.
2. dégradé :
   - provider absent,
   - sortie vide ou invalide,
   - reward backend indisponible,
   - pas de faux succès silencieux.
3. croissance :
   - topologie plus grande ou plus d'étapes,
   - plus d'un provider,
   - reroute / adaptation,
   - comportement toujours traçable.

H. CI
Améliore le verrouillage sans faire exploser le temps d'exécution.
Je veux au moins :
- un smoke test utile pour le contrat policy/runtime,
- un smoke test utile pour le mode Phase C retenu,
- un scénario dégradé,
- et une meilleure protection de la branche active ou des paths critiques.

Phase 4 — Docs en dernier
Seulement après code + tests verts :
- corrige README.md,
- corrige AI-ARCHITECTURE.md,
- fais-les refléter exactement la réalité du code.
Si quelque chose reste partiel :
- écris-le explicitement.
Pas de marketing.
Pas d'ambiguïté entre warm-up GRPO et vraie Phase C dynamique.
Pas d'ambiguïté entre régénération externe et mutation in-place.

Critères d'acceptation non négociables
Tu n'as atteint l'objectif que si :
1. la différence entre warm-up one-shot et vraie phase dynamique est claire dans le code, les scripts, les tests et la doc ;
2. il existe sur cette branche un chemin Phase C réellement runnable et testable ;
3. le contrat policy -> graph -> runtime est cohérent ;
4. le multi-provider est concrètement représenté dans le système adaptatif ou son contrat ;
5. les modes reward/fallback sont honnêtes et traçables ;
6. les tests/CI protègent les points critiques ;
7. la doc finale n'exagère plus rien ;
8. aucune capacité utile existante n'a été supprimée sans remplacement équivalent.
