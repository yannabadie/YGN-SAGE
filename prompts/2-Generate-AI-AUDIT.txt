## Mission

Tu réalises un audit technique hostile du repo YGN-SAGE à la branche/commit indiqué.
Tu dois falsifier les claims du projet, pas les reformuler.
Tu notes l’implémentation réelle, pas l’intention.

Ton objectif n’est pas de “couvrir les sujets”. Ton objectif est d’identifier les points où le projet prétend plus qu’il n’implémente.

---

## Portée et hiérarchie des preuves

Ordre de priorité des preuves :
1. Code réellement reachable depuis un point d’entrée runtime ou training
2. Tests, benchmarks, CI, scripts de lancement réellement utilisables
3. Configs, manifests de dataset, checkpoints, fichiers d’environnement
4. Documentation technique, AI-ARCHITECTURE, README

En cas de contradiction, tranche selon cet ordre.
Tu dois noter explicitement la branche et, si possible, le commit SHA réellement audité.

---

## Définition stricte de “implémenté”

Ne considère une capacité comme **implémentée** que si tu peux démontrer les 4 éléments suivants :
1. le fichier / symbole qui la porte,
2. le chemin d’appel depuis un point d’entrée réel,
3. l’état ou les données qu’elle lit/écrit,
4. un indice d’usage réel : test, benchmark, pipeline, CLI/API, ou config activée.

Sinon, classe la capacité dans une des catégories suivantes :
- `Doc-only`
- `Code mort`
- `Squelette`
- `Partiellement câblé`
- `Réel mais non validé`
- `Réel et validé`

Ne compte **pas** comme preuve :
- un README seul,
- une interface / trait / classe sans appel réel,
- un composant derrière feature flag non utilisé,
- un mock/stub/placeholder,
- un test purement structurel ou de sérialisation,
- un dossier “training” sans script de lancement + config + dataset loader + checkpoint path.

## Protocole d’audit obligatoire

Considère l’audit comme **incomplet** tant que chaque claim majeur n’est pas classé avec preuve ou blocage explicite.

Avant de conclure, tu dois obligatoirement :

1. Identifier les points d’entrée réels :
   - runtime / serving
   - training / fine-tuning / RL
   - tests / benchmarks / CI

2. Lister les composants critiques inspectés au minimum pour :
   - topology generation
   - routing / model assignment
   - memory
   - training / reward / datasets
   - pipeline principal
   - provider/model registry
   - tests / CI / benchmarks

3. Chercher explicitement les signaux de vaporware ou de fragilité :
   - TODO / FIXME / XXX
   - NotImplemented / unimplemented! / panic! / pass
   - mock / stub / placeholder / fake / dummy
   - sentinelles de reroute / fallback
   - seuils heuristiques hardcodés
   - env vars ou flags qui désactivent l’exécution réelle
   - coûts / latences codés à zéro
   - mémoire non persistée malgré un claim de mémoire durable
   - reward purement structurelle vendue comme performance réelle

4. Séparer strictement trois plans :
   - `Serving runtime`
   - `Training offline`
   - `Expérimental / dead code`

5. Pour chaque claim majeur, produire la chaîne :
   `Claim -> Evidence -> Reachability -> Validation -> Verdict`

6. Tester chaque mécanisme critique sous 3 scénarios :
   - `Nominal`
   - `Dégradé` : timeout, provider failure, sortie vide, latence haute
   - `Croissance` : plus d’agents, mémoire longue, coût, session longue, plus de topologies

7. Si une information manque, ne meuble pas.
   Dis exactement :
   - quel artefact manque,
   - pourquoi il bloque l’évaluation,
   - ce qui ferait changer le verdict.

## Format de preuve obligatoire

Chaque affirmation non triviale doit se terminer par 4 champs :

[EVIDENCE: path:lines ; symboles]
[STATUT: Observé | Inféré | Inconcluant]
[REACHABILITY: Runtime | Training | Dead code | Inconnue]
[VALIDATION: Test | Benchmark | Pipeline | Aucune]

Exemple de formulation acceptable :
“Le reroute est semi-runtime, car il existe un signal de reroute mais la reconstruction du graphe repasse par le pipeline externe au lieu d’une mutation in-place du DAG. [EVIDENCE: path:lines ; fonctions] [STATUT: Observé] [REACHABILITY: Runtime] [VALIDATION: Pipeline]”

Ne te laisse pas piéger par mes axes.
Si tu découvres un problème plus banal mais plus grave que mes thèmes initiaux
(ex. code mort, absence de tests, métriques factices, training non branché, mocks dans la reward, mémoire jamais relue, CI vide),

Pas de section bonus.
Mais aucun problème matériel ne doit être caché simplement parce qu’il n’entre pas proprement dans un axe.

## Comparaison à l’état de l’art

Quand tu compares à AutoGen, CrewAI, LangGraph, MetaGPT ou autres,
compare explicitement sur les axes suivants :
- reconfiguration runtime réelle ou non
- politique apprise vs heuristiques
- granularité d’adaptation
- mémoire/rétention
- coût/latence/qualité
- preuve expérimentale

Pas de comparaison marketing.
Pas de “proche de X” sans mécanisme précis.

## Axes d’analyse obligatoires

### 1. Génération topologique : adaptativité réelle ou déclarative ?

Réponds précisément à :
- Le mécanisme de génération topologique est-il réellement adaptatif ?
  Distinction obligatoire entre :
  - génération au design-time,
  - génération au démarrage,
  - reconfiguration par requête,
  - adaptation cross-run / cross-session.
- Quel est le feedback loop exact ?
  Trace complète obligatoire :
  `observation -> signal -> décision -> actuation -> effet sur exécution`
  avec noms de classes/fonctions.
  Si un maillon manque, est mocké, ou n’est pas branché, dis que la boucle est cassée.
- Quelle est la granularité d’adaptation ?
  Distingue clairement :
  - ajout/suppression réelle de nœuds,
  - rerouting externe au graphe,
  - changement de modèle par nœud,
  - modification de prompts/paramètres,
  - appel de sous-agent sans mutation du graphe.
- Comparaison avec l’état de l’art :
  compare uniquement mécanisme contre mécanisme.
- Verdict :
  positionne l’implémentation actuelle sur :
  `[Statique | Semi-dynamique | Dynamique réactif | Adaptatif avec apprentissage]`

Important :
- Une simple sélection initiale de topologie n’est pas de l’adaptation runtime.
- Un sous-agent appelé sans modifier le graphe n’est pas une mutation topologique.
- Un mécanisme derrière feature flag ou code mort compte comme absent.

### 2. Mémoire et apprentissage continu : viable ou vaporware ?

- La mémoire dédiée à la génération topologique existe-t-elle réellement ?
  Une mémoire n’existe que s’il y a :
  `write path + retrieve path + usage réel dans la décision topologique`
- Identifie les structures, le stockage, la persistance, la rétention, l’oubli, l’éviction.
- L’apprentissage continu est-il réellement implémenté ?
  N’appelle “learning” que ce qui modifie réellement une politique, des poids, ou un scorer réutilisé dans le main path.
- Si c’est du retrieval + prompt engineering itératif + few-shot contextuel,
  appelle-le ainsi.
- Évalue la scalabilité :
  compaction, summarization, eviction, bornes mémoire, coût de récupération.
- Verdict :
  `[Non implémenté | Squelette présent | Fonctionnel mais naïf | Production-ready]`

Important :
- Le logging n’est pas de la mémoire utile.
- Une DB qui stocke des épisodes mais n’influence jamais la décision n’est pas une mémoire d’apprentissage.

### 3. Choix du modèle à entraîner

- Le projet entraîne-t-il un modèle, ou orchestre-t-il surtout des modèles existants ?
- Distingue impérativement :
  - modèle d’exécution d’agent,
  - modèle de synthèse de topologie,
  - modèle de scoring/routing,
  - modèle de reward/judge.
- Si entraînement :
  exige preuve de :
  `trainer script + dataset loader + config + checkpoint/adaptateur + commande de lancement`
- Si orchestration :
  juge si le routing est réellement basé sur tâche/coût/latence/qualité,
  ou simplement sur règles fixes.
- Recommandation :
  propose le **meilleur candidat réel** à fine-tuner,
  ou conclue qu’aucun fine-tuning n’a de sens à ce stade.
- Dis clairement si le gain attendu vient plutôt de :
  `fine-tuning` ou `prompting + RAG + routing + évaluation`

### 4. Type d’entraînement : est-ce le bon ?

- Si SFT :
  évalue qualité/volume du dataset, diversité, risque d’overfit, oubli catastrophique.
- Si RLHF/DPO/GRPO/GiGPO/etc. :
  n’infère rien depuis les noms de dossiers.
  Vérifie :
  `reward function réelle + boucle d’update + exécution réelle ou simulée + intégration au serving`
- Si aucun entraînement :
  dis si c’est un choix rationnel ou une incapacité.
- Fais une estimation grossière coût/bénéfice :
  GPU-hours / cloud $
  mais seulement si des hypothèses minimales sont disponibles.
  Sinon dis que l’estimation serait trop spéculative.

Important :
- Une reward structurelle seule n’est pas une reward alignée sur la performance réelle.
- Un trainer externe non livré ou non branché doit être noté comme dépendance bloquante.

### 5. Améliorations — classées par impact

Propose exactement **5 améliorations**, classées par ratio impact/effort.

Pour chacune :

#### Amélioration N : [Titre]
- **Problème identifié** : [ce qui ne va pas, avec composant + preuve]
- **Impact si non résolu** : [conséquence concrète]
- **Solution proposée** : [implémentation concrète]
- **Effort estimé** : [jours-dev, complexité]
- **Papier/Référence** : [travail existant si pertinent]

Contraintes :
- Pas de généralités.
- Chaque amélioration doit viser un composant réel du repo.
- Ne propose pas de “réécrire le projet”.
